# Contributing to PostNot

PostNot welcomes bug reports, feature requests, review feedback, and agent-friendly task definitions.

This repository accepts **AI-generated contributions only**. Humans are welcome to propose work, curate prompts, review output, request reruns, and merge changes, but repository content submitted in pull requests should be generated by AI tooling rather than handwritten line-by-line.

If that workflow does not fit your contribution, open an issue instead of a pull request.

## Before You Start

Read these first:

- [README.md](README.md)
- [AGENTS.md](AGENTS.md)
- [docs/tech-design.md](docs/tech-design.md)
- [CHANGELOG.md](CHANGELOG.md)

Then check for an existing issue or open a new one using the repository's issue forms.

## What We Accept

Good contributions for this repo include:

- reproducible bug reports
- feature requests with clear user value and acceptance criteria
- bounded implementation tasks that an agent can execute
- AI-generated pull requests with validation evidence
- doc updates that keep the repo aligned with shipped behavior

## AI-Only Contribution Rules

For pull requests:

- The proposed repository content must be AI-generated.
- The pull request description must disclose the agent/tooling used and a short prompt or task summary.
- A human must review the generated output before submission.
- Contributors are responsible for making sure generated content is legal to submit and does not copy incompatible material.
- Maintainers may close contributions that appear manually authored, lack authorship disclosure, or are effectively unreviewed AI output.

## Workflow

1. Start from the latest `master`.
2. Use an existing issue or open a new one with enough detail for an agent to act.
3. Keep the change focused. Do not mix unrelated fixes, refactors, or release chores.
4. Keep docs aligned with behavior:
   - Update [docs/tech-design.md](docs/tech-design.md) when implementation meaningfully changes.
   - Update [CHANGELOG.md](CHANGELOG.md) for user-visible changes under `Unreleased`.
5. Run the relevant validation commands before opening a pull request.
6. Open the pull request with the repository template fully filled out.

## Validation

Frontend:

```bash
npm run check
```

Rust:

```bash
source "$HOME/.cargo/env"
cargo check --manifest-path src-tauri/Cargo.toml
```

Use `npm run tauri dev` when the change needs desktop behavior verification.

## Repo-Specific Expectations

- Preserve the local-first product model.
- Do not introduce cloud dependence, telemetry, or secret-handling regressions without explicit issue-level approval.
- Keep changes compatible with the current Rust + Tauri + SvelteKit architecture unless the issue explicitly calls for architecture work.
- Do not edit unrelated files just because an agent surfaced them.
- Call out known risks, skipped validation, and follow-up work in the pull request.

## Pull Request Expectations

Every pull request should include:

- the related issue
- a concise change summary
- validation evidence
- screenshots or recordings for visible UI changes
- known risks or intentionally deferred work
- AI authorship disclosure

Pull requests that do not provide enough context for efficient review may be sent back for clarification or closed.

## Security

Do not use public issues or pull requests for vulnerability disclosure. Follow [SECURITY.md](SECURITY.md) instead.
